# חדר מצב כסף

דשבורד פיננסי מקומי לעסק ישראלי. רץ על המחשב שלך; הנתונים נשארים בו, חוץ משלוש יכולות AI אופציונליות (`/review`, `/classify` והצ'אט "שאל את הנתונים") ששולחות תמצית ל-Claude, ורק אחרי שאישרת במפורש ולאחר בדיקת החיבור למנוי.

עונה על שלוש שאלות שרוב העסקים הקטנים לא יודעים לענות עליהן באמצע השנה:

1. **כמה באמת נשאר לי החודש** — הכנסות פחות הוצאות, מסווג אוטומטית מתנועות הבנק
2. **על מה יוצא הכסף** — פילוח הוצאות לקטגוריות, עם הספקים הגדולים
3. **כמה מזה באמת חייב במס** — הגשר מתזרים להכנסה חייבת, לפי כללי ההכרה בישראל

## למי זה מתאים

עוסק פטור · עוסק מורשה · חברה בע"מ. ההתקנה שואלת מה אתה, ומכוונת את הדשבורד בהתאם —
לעוסק פטור אין מע"מ ויש התראת תקרה, לחברה יש מס חברות ומשיכות בעלים.

## התקנה

צריך Node 20+.

```bash
git clone <this-repo> && cd money-dashboard-il
npm install
npm run dev
```

פתח http://localhost:8423. בפעם הראשונה הדשבורד פותח **מסך הגדרה** במקום נתונים:
סוג העסק (פטור / מורשה / חברה), שיעור המקדמות, מפתחות Financy לבנק, ואם יש,
מפתחות קארדקום לסליקה. לוחצים "שמור", הסנכרון הראשון רץ (דקה-שתיים), והדשבורד
נפתח עם כל הנתונים. כפתור "הגדרות" בכותרת מחזיר למסך הזה בכל רגע.

המפתחות נשמרים ב-Keychain במק, או בקובץ `.env` מוגן (מחוץ ל-git) בלינוקס/ווינדוס.
הם לא נכתבים לשום קובץ קונפיג ולא מוחזרים לדפדפן.

**מעדיף להתקין בשיחה?** עם [Claude Code](https://claude.com/claude-code) מותקן,
`claude` ואז `/setup`: אותן שאלות, פלוס כיול ראשון של חוקי הסיווג מול התנועות
האמיתיות.

## מאיפה מגיעים הנתונים

**דרך בנקאות פתוחה (Open Finance), עם [financy](https://www.npmjs.com/package/financy).**
נרשמים ל-Financy (שירות בתשלום — חשבון נפרד לכל עסק), מחברים את חשבונות הבנק
דרך התקן הבנקאות הפתוחה, ומקבלים שלושה מפתחות. סקיל ההתקנה שומר אותם ומכאן
הסנכרון רץ לבד:

```bash
npm run sync
```

נתוני הסנכרון עוברים ישירות מהבנק אליך דרך שירות מורשה. מסכי החישוב קוראים
מקומית; רק יכולות ה-AI האופציונליות שתוארו למעלה שולחות תמצית אחרי הסכמה ובדיקה.
הטלמטריה של Next מכובה מפורשות בסקריפטים
(`NEXT_TELEMETRY_DISABLED=1`), ו-CLI של Financy מוצמד לגרסה מדויקת ב-
`package.json` ורץ מ-`node_modules` בלבד, לא נמשך מהרשת בזמן ריצה.

**אם משהו אחר כבר מרענן את אותו חשבון Financy** (אפליקציה נוספת, MCP, cron):
קבע `financyRefreshEnabled: false` ב-`config/settings.json`. מכסת הרענונים
נספרת מקומית ואינה יודעת על צרכנים אחרים, ושני מרעננים על חשבון אחד שורפים
קרדיטים כפול.

**לפני שמעלים את התיקייה לגיטהאב:** `config/rules.json` ו-
`config/expense-rules.json` מתמלאים בשמות אמיתיים של עובדים, ספקים ולקוחות
שקיבלו החזר. הם קבצי גיט לכל דבר. ריפו ציבורי יפרסם אותם, וגם מחיקה מאוחרת
משאירה אותם בהיסטוריה.


## שני מסכים

**דוח מצב** (`/`): מה שרואים בבוקר. ארבע שורות קבועות (כסף · מכירות · מה מתקרב ·
שווה לבדוק), שלושה מספרים (יתרה, הנקודה הנמוכה הקרובה, התשלום הבא), "לטיפול"
בשלוש קבוצות (היום · השבוע · כשיהיה לך זמן) ומכירות 7 ימים עם סימון ✓ ליד יום
שהכסף שלו כבר בבנק. ביום שקט כתוב "אין מה לטפל היום." צבע אדום מופיע רק כשכסף
חסר או מועד עבר; עבודות תחזוקה (סיווג, מוטבים חדשים) לעולם לא אדומות.

**פירוט** (`/details`): החודש (בורר חודש, ערוצים, רו"ה, הוצאות) · מסים (מע"מ,
מקדמות, הערכה שנתית) · תזרים ונזילות (חשבונות, תחזית, מכירות, התאמת סליקה).

## מחזור לפי ערוץ

העסק מגדיר את ערוצי ההכנסה שלו (ליווי, קורס, ייעוץ, מוצרים...) במסך הפתיחה או
בפאנל. המחזור מתחלק ביניהם משני מקורות בלי כפל: מכירות קארדקום לפי שם המוצר,
והכנסות בבנק לפי שם המוטב (זיכויי סליקה מדולגים, הם אותו כסף). לפי חודש ולפי
שנה, עם אחוז מהמחזור. כל מה שלא זוהה יושב ב"לא משויך" עם כפתור שיוך: בחירת
ערוץ שומרת כלל ב-`config/channels.json`, וההיסטוריה מתעדכנת.

## תזרים קדימה: 30 / 60 / 90 יום

התחזית לומדת לבד מה קבוע: מוטב שחוזר ב-3 מתוך 6 החודשים האחרונים, באותו יום
בחודש (±4) ובאותו סכום (±25%), בשני הכיוונים (שכירות, משכורות, מסים, וגם לקוח
ריטיינר שנכנס ב-10 לחודש). פריט שחוזר כל חודשיים (מע"מ דו-חודשי) מזוהה ככזה.
מוסיפים לזה תנועות עתידיות שהבנק כבר מציג, וזיכויי סליקה שעדיין בחלון.

השורה החשובה: **נקודת השפל**, מתי היתרה הכי נמוכה, כמה, ומה ההכנסה הראשונה
אחריה. מתחת ל-`cashDipWarnIls` (ברירת מחדל ₪10,000) זה גם דגל.

"מה נלמד מהבנק" מציג את הפריטים עם "אשר" (נכנס ל-`config/recurring.json` → `items`)
או "לא קבוע" (נכנס ל-`ignore`). מה שלא סומן נשאר בתחזית כניחוש.

## מע"מ ומקדמות

**מע"מ.** לתקופת הדיווח האחרונה שנסגרה (חודשית או דו-חודשית, לפי ההגדרה או לפי
המחזור: מעל ₪1,775,000 חודשי): מע"מ עסקאות מההכנסות, פחות מע"מ תשומות מההוצאות
שנושאות מע"מ (`config/tax-rules.json` → `vatInput` קובע מה נחשב), מה נשאר לשלם
ועד מתי, והאם שולם. בנוסף: כמה נצבר לתקופה הפתוחה. זו הערכה לתזרים, לא הדוח
עצמו; הדוח נבנה מחשבוניות.

**מקדמות, מצטבר שנתי.** מד המקדמות החודשי עונה "שילמתי החודש?". הפאנל המצטבר
עונה "אני בקצב לשנה?": סך המקדמות ששולמו מתחילת השנה מול מס ההכנסה השנתי הצפוי
(מפאנל המס), הפער, כמה צריך לחודש בחודשים שנותרו, ואם שווה להגדיל או להקטין את
השיעור.

## מכירות מקארדקום (אופציונלי)

אם אתה סולק דרך קארדקום, הדשבורד מציג גם פאנל **מכירות**: היום, אתמול, שלשום,
7 ימים אחרונים, או כל תאריך שתבחר, עם פילוח לפי מוצר. `/setup` שואל אם
לחבר; צריך משתמש API לטרמינל עם הרשאת קריאה. המפתחות נשמרים כמו של Financy
(Keychain במק, `.env` מוגן בלינוקס/ווינדוס), והגדרות המודול ב-`config/cardcom.json`.

נשמרים רק מזהה עסקה, זמן, סכום ושם מוצר. פרטי הלקוח לא נכתבים לדיסק.

**התאמת סליקה ↔ בנק.** כל יום מכירות (או חודש, לפי הסדר עם חברת הסליקה) מקבל
שורה: כמה נסלק, כמה צפוי להיכנס לבנק אחרי עמלה, ומה קרה בפועל: נחת / פער /
ממתין / **לא נחת**. זיכוי שלא הגיע הופך לדגל אדום. ההגדרות (מועד זיכוי, עמלה,
סטייה מותרת, איך הזיכוי נראה בבנק) ב-`config/cardcom.json` → `settlement`.

```bash
npm run sync                          # בנק + קארדקום (היום)
npm run sync:cardcom -- --backfill 90 # טעינה היסטורית
```

## מצב הדגמה — ללמד בלי לחשוף כלום

רוצים להראות את הדשבורד למישהו, להקליט סרטון, או ללמד סדנה — בלי נתונים אמיתיים?

```bash
npm run demo && npm run dev
```

זה מייצר **עסק פיקטיבי** — 8 חודשים של תנועות מציאותיות שנספרים אחורה מהיום,
לקוחות מומצאים, מסים, פרסום ותוכנות — שמדליק כל פאנל בדשבורד. הנתונים דטרמיניסטיים: כל הרצה מייצרת
בדיוק את אותם מספרים, אז הקלטה ושידור חי תמיד יתאימו.

שלושה תסריטים:

```bash
npm run demo                        # עוסק מורשה — הסיפור המלא
npm run demo -- --entity=patur     # עוסק פטור מתקרב לתקרה → מדגים את ההתראה
npm run demo -- --entity=company   # חברה בע"מ — מס חברות ומשיכות בעלים
```

מצב ההדגמה **מסרב לרוץ** אם יש כבר נתונים, קונפיג שונה מברירות המחדל
(`config.defaults/`), או פלט של סוכנים. `--force` מגבה קודם את הקונפיג ל-`data/config-backup-*`
ורק אז מאפס. חזרה לעסק האמיתי: להעתיק את הגיבוי חזרה ל-`config/` ולהריץ `npm run sync`.

## אמינות הנתונים: בדיקות + סוכן פיננסי

דשבורד שמציג מספר שגוי בביטחון גרוע יותר מדשבורד שלא מציג כלום. לכן יש שתי שכבות
שעובדות בשבילך:

**שכבה 1, בדיקות קבועות (`scripts/lib/quality.mjs`).** רצות בכל טעינה, בלי AI:
תשלום קבוע שמופיע גם ידנית וגם נלמד מהבנק (נספר פעמיים), תשלום ידני שלא נראה
בבנק שלושה חודשים, חברת סליקה שהכסף שלה מעולם לא הגיע לחשבון הזה, יום חיוב של
מע"מ/מקדמות שלא תואם להגדרות, הערכת מע"מ רחוקה ממה ששולם בפועל, תנועות עתידיות
כפולות, חלק גדול מההוצאות בלי סיווג, חשבון מט"ח בלי שער, סנכרון ישן. התוצאה
מופיעה ב"פירוט ← אמינות הנתונים", והאריח "צפי תזרים" במסך המצב אומר כמה אפשר
לסמוך על התחזית. ממצאים ברמת "לתקן" נכנסים לרשימת "לטיפול ← השבוע", אף פעם לא
ל"היום": כלום כאן לא באיחור.

**שכבה 2, הסוכן הפיננסי (`/review`).** רואה חשבון פנימי שעובר על המספרים שבמסך
ועל ממצאי שכבה 1, ואומר בעברית פשוטה מה נכון, מה כנראה שגוי ומה לתקן, בארבע
כותרות קבועות: השורה התחתונה, מה נראה לא נכון, מה לתקן, שאלות לבעל העסק.

```bash
npm run review        # סקירה מלאה, נשמרת ל-data/review/ ומוצגת בדשבורד
/review               # בתוך Claude Code: אותו סוכן, בשיחה, יכול גם לתקן קונפיג אחרי אישור
```

**מה יוצא מהמחשב, ומתי.** הסוכנים והצ'אט שולחים ל-Claude תמצית של הנתונים: שמות מוטבים,
תאריכים, סכומים, תיאורי תנועות, יתרות ושמות חשבונות, שמות מוצרים, דוגמאות מחוקי
הסיווג, ובצ'אט גם השאלות שלך ותוצאות השאילתה. הקוד אינו מצרף בכוונה שדות סיסמה
או מפתח, אבל טקסט שתכתוב או מידע רגיש שנמצא בשדה שנשלח ייכלל בתמצית. אל תכתוב
סודות בצ'אט. השליחה מתבצעת רק
אחרי אישור מפורש (`npm run review -- --yes`, נשמר ב-`config/settings.json →
agentsSendDataToClaude` + `agentsConsentVersion`). ההסכמה מגורסת: כשסוכן חדש
שולח יותר (כמו הצ'אט), המספר עולה והסוכנים מבקשים אישור מחדש, לא מניחים אותו.

**בדיקת המנוי ובידוד הריצה.** `npm run review` ו-`npm run classify` מפעילים התקנת
Claude Code מנתיב קבוע ומאומת, לא פקודה שנמצאה ב-`PATH`. אותו קובץ הרצה ואותה
סביבה מינימלית משמשים גם ל-`claude auth status` וגם למודל. הבדיקה דורשת claude.ai,
`firstParty` ומנוי שמופיע ב-`settings.json → agentsAllowedPlans` (ברירת מחדל
max/pro; Team/Enterprise אינם ברשימה כי הם יכולים לקבל ניתוב מנוהל שאי אפשר לסרוק
מקומית). הריצה משתמשת ב-`--setting-sources ""`, בלי כלים, MCP, פקודות slash או
Chrome, ומשביתה במפורש attachments, זיכרון אוטומטי, `CLAUDE.md`, policy skills,
הוראות Git, טלמטריה ותעבורת רקע. משתני proxy, TLS, OTEL, טעינת קוד Node ו-debug
בירושה גורמים לסירוב, וכך גם הגדרה או התאמה מנוהלת (`managed-settings.d`, hooks,
plugins, skills, `CLAUDE.md`) ופרופיל MDM/Registry של Claude Code.

**מה שאי אפשר להוכיח לחלוטין.** בדיקת ההתחברות ותהליך המודל הם שני תהליכים
עוקבים. הקוד מצמיד את שניהם לאותו executable ולאותה סביבה, אך אינו יכול למנוע
שינוי חיצוני של קובץ ההרצה או מצב ההתחברות ביניהם, או להוכיח כיצד שירות חיצוני
מטפל בבקשה. מתוך סשן Claude Code שכבר פתוח אי אפשר גם לאמת את ספק הסשן האב; לכן
המסלול הזה כבוי כברירת מחדל (`agentsAllowInteractive: false`). יש להתיר אותו רק
אם ידוע שהסשן על המנוי. ריצת review/classify מוגבלת ל-10 דקות, התוצאה נכתבת אטומית, ותשובה
בלי ארבע הכותרות נדחית. הסוכן לעולם לא משנה קבצים בריצה האוטומטית; באינטראקטיב
הוא מציע ומחכה ל"כן". שמות מוטבים מהבנק מסומנים לסוכן כנתונים, לא כהוראות.

**שכבה 3, סוכן הסיווג (`/classify`).** תנועה בלי קטגוריה מקלקלת מע"מ, מס, רווח
ותזרים בבת אחת. הסוכן עובר על כל המוטבים שנשארו "לא מסווג", מציע לכל אחד קטגוריה
עם הסבר ("הוט מובייל: טלפון, הוצאה עסקית שוטפת") ורמת ביטחון, ואתה מאשר ברשימה
אחת בדשבורד (פירוט ← אמינות הנתונים ← סיווג). החוק הוא חוק-מחרוזת ("כל מוטב שמכיל
'הוט מובייל'"), והפאנל מראה לפני האישור על אילו מוטבים נוספים הוא יחול. אישור שומר
את החוק במסד (טבלת `classify_rules`, קודם לכל חוק ב-`rules.json`) ומריץ סיווג מלא
מחדש באותה טרנזקציה, בדיוק מה שהסנכרון הבא היה עושה. החלטה חדשה גוברת על ישנה.
חוק שאושר בטעות מבטלים באותו פאנל ("חוקים קבועים" ← בטל): החוק נמחק, הסיווג רץ
מחדש, וההצעה נפתחת שוב. ההצעות וההחלטות נשמרות גם הן במסד (`classify_proposals`). "לא" רק מסתיר את ההצעה.

```bash
npm run classify      # snapshot נשמר ב-data/classify/; ההצעות וההחלטות נשמרות ב-SQLite ומחכות לאישור בדשבורד
```

**שכבה 4, שאל את הנתונים.** צ'אט במסך המצב: "כמה כסף נכנס לבנק בחודש שעבר?", "על
מה יצא הכי הרבה החודש?", "מי הלקוחות הגדולים ברבעון?". בדרך כלל זו קריאת Claude
אחת עם חבילת נתונים מוכנה (13 חודשים: כניסות ויציאות לפי קטגוריה, המוטבים
הגדולים, חיובי כרטיס, מכירות, יתרות). לשאלה שהחבילה לא מכסה המודל מבקש שאילתת
SELECT אחת, היא רצה עד 10 שניות על מסד-צל לקריאה בלבד (200 שורות לכל היותר), ואז
מתבצעת קריאת Claude שנייה; "איך חישבתי" מראה את השאילתה. בדרך כלל התשובה מגיעה
בתוך שניות, אך כל קריאת מודל מוגבלת ל-3 דקות. שאלה אחת מטופלת בכל פעם. אותו שער
כמו שאר הסוכנים: הסכמה (גרסה 2, כי הצ'אט משתף יותר), בדיקת מנוי ובידוד הריצה.

לסקירת בוקר אוטומטית: משימה מתוזמנת שמריצה `npm run sync && npm run classify && npm run review`.

## מה זה לא

**זה לא ייעוץ מס וזה לא תחליף לרואה חשבון.**

שכבת המס מציגה **הערכה בטווח**, לא מספר. היא מסתמכת על אחוזי הכרה שנכונים לכלל
המקרים, ועל נתונים שהיא רואה בלבד — הוצאה ששולמה מכרטיס שלא חיברת פשוט לא קיימת
מבחינתה. מדרגות המס ושיעורי הביטוח הלאומי ב-`config/tax-brackets.json` נושאים
מקור ודגל אמינות, ו-`verifiedBy` נשאר ריק עד שרואה חשבון מאשר אותם.

אל תגיש דוח על סמך מספר מהכלי הזה בלי לאמת אותו.

```
  expense-rules.json קטגוריות הוצאה

  settings.json      מע"מ (תדירות, יום דיווח), שיעור מקדמה, סף אזהרת תזרים
  recurring.json     קבועות ידניות + רשימת התעלמות; הלמידה האוטומטית משלימה
  channels.json      ערוצי הכנסה + כללי שיוך (מוצר / מוטב / סכום)

components/      הפאנלים
```
